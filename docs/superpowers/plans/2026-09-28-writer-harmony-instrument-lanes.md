# Writer: Harmony lane instruments and categorized section saves

**Status:** User approved; implementation in progress. Existing uncommitted groundwork is being audited against this plan. Duplicated Harmony lanes initially share Save IDs; creating a standalone Save and explicitly replacing a Writer chord is the route to divergence.

## Goal

Give each project a default Harmony instrument (Piano or Fretboard). New sections start with one real Harmony Lane using that project default; additional Harmony Lanes can use either instrument and remain instrument-bound. Every chord added through Add chord produces one visible Harmony block and one canonical, instrument-native SaveEntry in that section's Harmony category folder. Organize Writer saves under each section by lane category, creating each category only when a lane of that kind is created: Harmony, Save/Voicing, Drum, Melody, Guitar Strum, and Audio.

## User direction and working decisions

- The user selected an app-wide default Harmony instrument in Settings. If no value is configured when creating the first project, ask for Piano or Fretboard before creating the project; cancellation creates nothing. Persist the choice in Settings and copy it into that project's `ProjectConfig`. Later global setting changes affect only future projects. Every newly created section gets a primary Harmony Lane using its project's saved default. A secondary Harmony Lane has one instrument identity selected before it is created.
- An empty Harmony grid uses the existing Harmony Lane's instrument. If there is no Harmony Lane, use the project's default and create the lane only as part of a successful content commit.
- The user authorized clearing persisted app data because the app is unreleased and in testing. Before simulator verification, clear the test simulator's local app data once and create a fresh project. Do not add a recurring startup reset to the app.
- There is no “Quick Creation” action in scope. Each **Add chord** creates exactly one visible Harmony block and one canonical SaveEntry in the section's Harmony folder. That SaveEntry retains the symbolic Writer chord data and the chosen instrument's native realization. Do not create a second Save/Voicing lane or visible Save block for this action. Other explicit native Save placements remain available in Save/Voicing lanes.
- The chord editor path of Add chord authors a new composite Save in that Harmony folder. **From library** creates a placement that reuses the selected compatible composite SaveEntry; it does not copy or move the source Save. Manual entries stay physically in their original folder and appear in the section through the Writer link. For a Harmony chord, **Create standalone Save** copies the composite to the project root without changing a Writer block; **Replace chord** later binds it to a selected placement. Harmony must not use the existing detach-and-rebind meaning of **Make Unique**; that action remains unchanged for other Writer lane kinds.
- Only entries whose Harmony instrument matches the destination Harmony Lane can be used as Harmony chord saves. A chord's instrument identity comes from its Harmony Lane; its Save snapshot records the same identity and cannot be silently reused under another instrument.
- Create a shared category subfolder on demand when the first lane of that kind is created in a section. Distinct lane instances of the same kind share the folder; sections do not get unused category folders.
- A Harmony Lane's instrument is fixed while it contains blocks; allow changing it only when it has no chord blocks or dependent native Save/Voicing blocks. Since the app is unreleased and test data may be reset, do not build legacy Harmony Lane assignment or old-data migration paths. Legacy symbolic blocks have no inferable instrument; clear the test simulator data once, and require an explicit destination instrument before any future import/reuse path commits one.
- App Settings holds the optional global default Harmony instrument. New-project creation asks for it if unset, then persists it and copies it into that project's `ProjectConfig`; later changes to the global setting affect future projects, while existing projects keep their saved default.
- Duplicating a Harmony Lane copies its chord blocks with new block IDs that initially reuse the same canonical Harmony Save IDs. Before editing any Harmony Save linked to multiple blocks, warn and offer **Update all placements** or **Create standalone Save**. The latter creates a standalone manual Save in the project root and leaves every Writer block/link unchanged, regardless of where editing started; the user can later replace one chord in Writer. Lyrics remain placement-local. The block-level **Create standalone Save** action uses the same non-mutating behavior. Do not create an empty lane when the user chooses duplicate.
- Fretboard policy is to generate a playable fingering for every chord quality offered by Add chord; if no fingering fits the current tuning/capo/fret-range settings, Add chord shows an actionable error that those settings need adjustment and commits no block or SaveEntry.

Whenever an edit targets a Harmony Save linked to multiple Harmony Writer blocks, Piano/Fretboard must first warn and offer **Update all placements** or **Create standalone Save**. The latter creates a `SaveOrigin.manual` SaveEntry in the project root and leaves all existing blocks/links unchanged. Later, in Writer, the user can choose **Replace chord** on an existing Harmony block and select that standalone Save; only that block's chord/Save link changes, preserving its section, lane, bar, duration, repeats and local lyrics. The selected Save must match the destination Harmony Lane's instrument and remains physically in the project root after linking.

## Proposed data shape

Add `HarmonyLaneInstrument` in a small standalone model file to avoid adding a new model dependency cycle, an app-level `AppSettings` default, a `ProjectConfig` copy of that default and a nullable serialized lane field because `SongLane` is shared by non-harmony lanes. Global `settingsProvider` is the source when creating a project; the selected project's `SaveFolder.projectConfig` is then the source for new sections in that project. `SongwriterConfig` remains the separate tempo/meter/key configuration. Every Harmony Lane must have a non-null instrument; non-harmony lanes must not carry one. Test app-settings/project-config/lane/snapshot serialization round trips; no old-data migration is required after the authorized one-time simulator reset.

```dart
enum HarmonyLaneInstrument { fretboard, piano }

class ProjectConfig {
  final HarmonyLaneInstrument defaultHarmonyInstrument;
}

class AppSettings {
  final HarmonyLaneInstrument? defaultNewProjectHarmonyInstrument;
  // Null until selected in Settings or during first-project creation.
}

class SongLane {
  final HarmonyLaneInstrument? harmonyInstrument;
  // Required for harmony lanes; null for all other lane kinds.
}

class HarmonyChordSnapshot extends InstrumentSnapshot {
  final HarmonyLaneInstrument harmonyInstrument;
  final WriterBlockSnapshot writerBlock;
  // Exactly one of PianoSnapshot or FretboardSnapshot; instrument identity
  // and native snapshot type must agree.
  final InstrumentSnapshot instrumentState;
}
```

The snapshot is composite content inside one `SaveEntry`; it is not a second Save or timeline placement. Its native pane opens the normal Piano/Fretboard editor, while Writer restores chord-symbol data from `writerBlock`.

At chord creation, the transaction builds the two representations together and links that one entry:

```dart
final writerBlock = writerBlockSnapshotFor(project, lane, block);
if (writerBlock == null) return; // No symbolic chord data; no partial write.
final snapshot = HarmonyChordSnapshot(
  harmonyInstrument: lane.harmonyInstrument!,
  writerBlock: writerBlock,
  instrumentState: createChordRealization(
    chordNotes: block.chordNotes,
    instrument: lane.harmonyInstrument!,
    instrumentContext: activeInstrumentContext,
  ),
);
```

The Piano/Fretboard editor adapter unwraps `instrumentState` for the existing instrument screen and rewraps it on save; the Writer store unwraps `writerBlock` for chord/lyric recovery. Validate that the wrapped concrete snapshot matches `harmonyInstrument` at construction and deserialization.

Add the optional global Harmony instrument default to `AppSettings` and the app Settings screen; persist it through `SettingsNotifier`. If it is unset when the user creates the first project, request Piano or Fretboard before committing the project; cancellation leaves app/project state unchanged. Persist that choice and copy it into the new project's `ProjectConfig`. Existing projects and their sections keep their persisted project default after the global preference changes. Read the per-project default from the selected project folder via a `SongwriterNotifier` helper, not from `SongwriterProjectSnapshot.config`, whose `SongwriterConfig` has only key/tempo/meter. Named Writer snapshots preserve concrete lane identities and do not change the project default. Changing the global setting does not retrofit existing projects, sections, Harmony Lanes or saves. `makeSection`/`addSection` seed a real primary Harmony Lane with that project default; direct and imported section creation must do the same. `addLane` accepts an explicit instrument for secondary Harmony Lanes and rejects one without it. An empty-grid Add chord uses the existing Harmony Lane instrument or the project default and stages creation until a chord or compatible Harmony Save is ready. Cancel does not leave a lane or block. Both library entry points—the chord sheet's **From library** branch and direct **Add from library** action—show only compatible composite Harmony chord saves and return a staged selection instead of mutating while a sheet is open. An instrumentless legacy `WriterBlockSnapshot` Harmony save is not a compatible Harmony Save and must not be reused as one; the authorized one-time data reset means no migration/conversion path is needed. Re-read project state and verify section, lane and bar before one atomic store command commits the block/save. Preserve the existing silent-block path, repeat-based verse count and primary-lane lyric write. The async ensure path must return the committed lane ID instead of mutating state inside the current synchronous callback.

For a handoff into a project with no sections, construct a temporary eight-bar `SongSection` with a generated stable ID and show that draft in `WriterBarTarget` selection. Extend `addSection` to accept that ID when committing. Stage the section, selected lane, block and Save write until destination, any required new-Save name, and replacement confirmations are complete; reuse skips the name prompt and never renames or edits the selected Save. Then commit as one history step and through the Writer journal. Cancel at any point leaves no section, lane, block or save behind. Re-read project, section, `laneId` and bar after every await before committing.

```dart
final instrument = lane.harmonyInstrument ??
    notifier.projectDefaultHarmonyInstrumentForSelectedProject;
final choice = await collectHarmonyCellChoice(
  context,
  instrument: instrument,
  filterLibraryTo: instrument,
);
if (choice == null || !context.mounted) return;
final current = ref.read(songwriterProvider);
if (!current.sections.any((s) => s.id == section.id && bar < s.lengthBars)) {
  return;
}
final inserted = notifier.commitHarmonyCellChoiceAtomically(
    sectionId: section.id,
    laneId: lane.id.isEmpty ? null : lane.id,
    harmonyInstrument: instrument,
    bar: bar,
    verseIndex: instanceIndex,
    verseCount: section.repeat.clamp(1, 16),
    isPrimary: isPrimary,
    choice: choice,
  );
if (!inserted) return; // Stale, incompatible or overlapping: no mutation.
```

The pseudocode above describes the commit boundary, not literal helper APIs. The store command must repeat validation of the selected Harmony SaveEntry, instrument, bar and overlap inside the same transaction that creates/reuses lanes and inserts content. For an authored chord, it creates both the symbolic Harmony block and its composite SaveEntry in the Harmony folder. It preserves the current `isSilent` branch and primary-lane lyric write; a stale or rejected library placement must not leave a Harmony Lane, SaveEntry or history entry behind.

## Folder and link design proposal

Keep current project and section folder identities. Under each section, create one managed category folder for a `SongLaneKind` when the first lane of that kind is created; do not create empty category folders for lane kinds not present in the section. Key each folder by stable section ID plus lane kind. `WriterSaveLink.folderId` points to the category folder and its `laneKind` must match that folder. Place new Writer-origin `SaveEntry` objects physically in their category folder. Preserve a manual `SaveEntry` in its existing physical folder during normal reconciliation (often project root); the Writer link makes it appear virtually in the section's matching category folder, as it does today for section folders.

```text
Project
└── Verse
    ├── Harmony
    ├── Save / Voicing
    ├── Drum
    ├── Melody
    ├── Guitar Strum
    └── Audio
```

Use additive metadata on `SaveFolder`: the section root keeps `writerSectionId` with no `writerLaneKind`, and each category folder keeps the same section ID plus its lane kind. Create a category folder only when a lane of that kind is created in the section; this preserves empty-space-free sections while ensuring the default Harmony lane has a Harmony folder. This preserves `getWriterSectionFolder`'s root lookup. Writer-origin Harmony composite SaveEntries live in the Harmony folder, Writer-origin native Save placements live in Save/Voicing, and every WriterSaveLink points at its lane-category folder. A standalone manual Harmony Save remains physically in the project root after replacement. Update nested-folder helpers including `getWriterLinksForSection` and `writerSaveFolderForLinks`. A link must resolve to a category inside its project/section subtree and match `laneKind`; it must no longer require `WriterSaveLink.folderId` to equal the section root. Compute section deletion from actual folder ancestry (the full `getSubtreeFolderIds` result), including descendants without Writer metadata. Normal reconciliation never moves manual saves. If a manually moved/imported manual `SaveEntry` physically lives inside a managed section subtree that is about to be deleted, preserve it by moving that entry to the project root before removing the subtree; keep its ID, name and snapshot. Permit this narrow same-project move in `buildWriterStructure` only when the source folder is in the removed section subtree and the destination is the selected project root. Keep it inside the existing Writer journal transaction and cover it with a test.

Preserve a Writer-origin SaveEntry's current physical `folderId` whenever that folder still exists in the selected project. Adding/reordering cross-section Writer links must never move the Save merely because another linked section sorts earlier; each placement is represented by its own `WriterSaveLink` and virtual section-category membership. If the physical folder is deleted with its managed section subtree, rehome the Save into a surviving linked category folder chosen by section order then lane order; if no linked category survives, use the project root. Manual SaveEntries retain the separate rule above: normal linking never moves them, and only deletion of their physical ancestor can trigger same-project preservation at root.

```dart
final currentFolder = folderById[save.folderId];

In `song_from_writer_rules.dart` and `songwriter_playback_rules.dart`, only null anchors may use the primary-lane fallback; stale explicit anchors must not render, mix, play, or export under another Harmony Lane. ## Plan review checklist

- The global default instrument is persisted and editable in app Settings. If unset before first-project creation, the app asks for Piano/Fretboard and saves that choice; new projects copy it into `ProjectConfig`, and each new section uses it for its primary Harmony Lane. Secondary lanes have an explicit selected tool and retain it on rename/reorder/project reload. Changing the global setting does not alter existing projects.
- A chord authored by **Add chord** creates one visible Harmony block, one linked `HarmonyChordSnapshot` SaveEntry in the section's Harmony folder, and no Save/Voicing lane or extra visible block. **From library** reuses one same-instrument composite SaveEntry and its shared-edit behavior. **Create standalone Save** copies both halves to a manual project-root Save without rebinding any block; **Replace chord** explicitly rebinds only the chosen block. The composite round-trips through Save Browser/native editing, chord editing, restore, undo/redo and persistence without losing either its Writer or native fields.
- Piano/Fretboard **Use in Writer** on a Harmony composite stored anywhere in the selected project asks the user to choose section, compatible Harmony Lane, and bar, then reuses the same Save ID without renaming, moving or editing the Save and creates no Save/Voicing lane.
- Updating a Harmony Save used by multiple Writer blocks from Piano/Fretboard warns first and offers **Update all placements** or **Create standalone Save**. The standalone choice saves the edited composite at project root and leaves existing placements unchanged; later, Writer **Replace chord** rebinds only the selected block while preserving position and lyrics.
- Harmony Save library entries match the destination lane instrument; unrelated native saves and symbolic Writer saves without instrument identity cannot be misrepresented as compatible. Both library entry points stage selection and commit atomically. Cancel, stale destination, overlap, and instrument mismatch leave no partial lane/save/block/history state. Preserve silent placeholders, verse counts and primary lyrics.
- Piano chord realization maps every chord tone deterministically. Fretboard search uses the instrument's tuning/capo and configured fret range to find a playable shape for each offered chord quality. If the current valid settings have no shape, show an actionable error about changing the instrument settings; do not mutate the project or automatically widen the range.
- `WriterBarTarget` carries specific lane identities; handoff source instrument is derived at the boundary, compatible destination lanes are filtered, and a staged lane/section commits only after all prompts succeed. Native instrument snapshots inserted as explicit Save blocks target a Save lane anchored to a same-instrument Harmony Lane.

Null primary anchors are valid; stale explicit anchors never fall back to primary. Stale Save and Guitar Strum lanes remain visible/repairable and do not render, mix, play or export under an unrelated lane.
