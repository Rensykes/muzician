# Songwriting Workflow Improvement Plan

**Status: Implementation complete; fresh-context final review approved v17. Approved plan revision: v15.**

## Product Outcome

Help a songwriter capture an idea, develop it with guitar and piano, arrange it into a song, and produce a complete demo without losing context or work. The existing Writer, Song, Fretboard, Piano, Piano Roll, and save system remain the foundation. This initiative closes workflow gaps around them.

## Evidence From the Current App

- The first-run tab is Fretboard (`_tabIndex = 0`); Writer and Song are separate destinations in the six-tab navigation.
- Fretboard and Piano support note preview, chord/scale exploration, and saveable selections. Writer's instrument-library path depends on saves, so an idea may require a tab switch and a library lookup before it becomes part of a song.
- Writer supports song sections, repeated sections, harmony and saved-voicing lanes, lyrics, drums, audio lanes, playback, and a section mixer.
- Song is a fuller clip arranger with note, drum, and audio tracks, transport controls, recording/import, and a Writer import path.
- Song WAV export currently excludes audio clips. Recorded takes are committed without a review step, and audio assets are stored locally rather than packaged for another device.
- The README feature table now lists Writer and Song, but its project-structure documentation list is incomplete. `docs/songwriter.md` still calls Writer foundation-only, and `docs/song_workspace.md` contains capability statements that conflict with the newer Song & Writer guide.

## Principles

1. Writer is the clearest first workspace for songwriting; instruments remain one step away.
2. Preserve the current section/bar context when moving between instruments and writing.
3. Reuse established models and playback paths when adding melody or guitar rhythm.
4. Make recording review, destructive actions, save state, and export limitations explicit.
5. Update `PRODUCT.md`, `DESIGN.md`, `AGENTS.md`, `README.md`, and feature guides as behavior or guidance changes.

## Delivery Phases

### Phase 1 — Songwriting Entry and Instrument Handoff

- Startup preflight also inspects every known legacy save-system and singular session key before the existing migration/wipe path can remove them. Validate each legacy blob using its source schema; malformed values enter the same raw-preservation flow and are not deleted until the user confirms Start fresh. Valid legacy values continue through the existing migration policy.
- Recovery export filenames include both a sanitized source key and a unique backup identifier so two saved payload types or two backups of one type do not collide. The initiating control supplies `sharePositionOrigin` to the iOS/iPadOS share sheet. On Web, `share_plus` opens the browser's Web Share API when available and uses its download fallback otherwise; success/cancel feedback reflects the actual share result rather than claiming a download unconditionally.
- Until session/save-system hydration completes, render only a startup loading view and do not mount the workspace `IndexedStack`; this prevents edits against pre-hydration state. A settings read failure uses default settings and does not block startup. For an I/O failure in session/save-system hydration, keep workspaces unmounted and offer Retry. For malformed persisted session or save-system JSON, preserve the original raw payload without deleting or overwriting it and show Recovery actions: Retry, or Start fresh while first copying the raw payload to a recovery key. Do not create or persist default content over the original payload before that explicit choice. After a fresh start, expose preserved payloads from **Settings → Data Recovery** as read-only text entries with Copy, Export, and confirmed Delete actions. Copy uses the original stored string; Export writes those exact bytes without JSON decoding/re-encoding (Android/iOS: share the `.json` file through the native share sheet; macOS/Windows/Linux: use the file save dialog; Web: invoke the share sheet when available and otherwise download through its fallback). Confirmed Delete removes only the selected recovery backup; keep the active project and other recovery payload entries unchanged. Backups remain until the user explicitly deletes them. Phase 1 adds [`share_plus: ^12.0.2`](https://pub.dev/packages/share_plus/versions/12.0.2) to implement Android/iOS share sheets and Web share/download. Upgrade Android Gradle Plugin from 8.11.1 to 8.12.1 to satisfy this version's Android requirement; keep Gradle 8.14, Kotlin 2.2.20, and Java 17. Retain the current `file_picker` 8.x dependency: `share_plus` 12 stays on the compatible `win32` 5 dependency line, avoiding the `win32` 6 migration and `file_picker` API upgrade. macOS/Windows/Linux use `file_picker` without bytes and then write the exact output bytes to the selected path. After successful hydration or an explicit fresh-start recovery, open Writer on first install or restore the last valid content workspace (`Fretboard`, `Piano`, `Roll`, `Song`, or `Writer`). Store only content-workspace selections in the settings preference; visiting `Settings` never replaces the saved content workspace. Missing or invalid preferences fall back to Writer. Navigation continues if writing the preference fails, but the next start uses the last successfully persisted value. Do not persist a workspace selection before hydration finishes.
- Clarify Writer as the section/chord/lyric sketch and Song as the clip arrangement workspace through labels and concise contextual help.
- Add a direct action from Fretboard/Piano selections to insert the detected chord or exact voicing into a chosen Writer section/bar. A detected chord becomes a harmony block carrying its symbol, root, quality, and selected pitch names. An exact instrument selection becomes a save-lane block with an embedded `InstrumentSnapshot`; neither path requires creating a library save.
- If no project is selected, retain the transfer payload while opening the existing project picker; cancel leaves both workspaces untouched. If Writer has no section, offer to create the existing default eight-bar section before choosing a bar. If a target bar is occupied, offer replace-with-confirmation, choose-another-bar, or cancel; do not rely on the store's silent overlap rejection.
- If the active project changes while the target picker is open, cancel the transfer and explain that the destination changed. Keep a useful empty state and an obvious way to start a section.
- Detect occupied bars from expanded lane placements (`tileLaneBlocks`), not only the source blocks, so repeated lane tiles are visibly occupied. When the user confirms replacing a repeated placement, map it back to its source block and replace that block's chord/snapshot in place, preserving its source start bar, span, and ID. Every expanded copy then reflects the replacement at the same repeated offsets; do not insert a new block at the selected expanded bar or change the lane's repeat pattern. The confirmation must explain that all copies change together.

### Phase 2 — Playable Melody and Guitar Rhythm

- **Existing Piano Roll layout follow-up:** the 1180×820 workspace currently overflows in the landscape quick-add button at `lib/features/piano_roll/piano_roll_screen_v2.dart:1127` (269 px) and in the edit/pitch control rows at lines 796 (87 px) and 846 (10 px). The quick-add row still overflows by 114 px at a generous 1800×1000 app mount. Fix these responsive controls as part of the Phase 2 editor work; melody editing depends on the existing Piano Roll.
- Extend `SongLaneKind` with `melody` and `guitarStrum`. Reuse `SongBlock.patternId`, interpreted by lane kind, to reference new `SongwriterProjectSnapshot.melodyPatterns` (`NotePattern`) and `guitarStrumPatterns` (`GuitarStrumPattern`) collections. Old JSON without either collection loads as empty.
- Both pattern types use local tick zero as the origin at the start of their `SongBlock`. Each pattern has a loop length; it repeats from the block origin until `block.spanBars * config.measureTicks`, and the final loop is clipped at that boundary. A note crossing a pattern-loop or block boundary is clipped there. Moving a block changes its timeline origin without changing pattern data; resizing changes the playback window/repeat count without deleting hidden pattern content. `tileLaneBlocks` creates repeated placements and `expandSections` repeats those placements.
- Define tempo as quarter notes per minute on both Writer and Song. The shared musical grid has four ticks per quarter note (one tick is a sixteenth note); `SongwriterConfig.measureTicks` and `TimeSignature` determine ticks per bar, but never change tick duration. Use one shared tick-to-duration rule, `60,000 / (tempo * 4)` ms per tick, in Writer live playback, Song live playback, and WAV export. In 6/8, for example, a bar has 12 ticks and lasts 1.5 seconds at 120 BPM. This replaces the current WAV renderer's beat-unit-dependent tick duration.
- A melody pattern stores existing `NotePatternNote` values (MIDI pitch, pattern-local start tick, duration ticks) and is edited with the existing Piano Roll editor; hum-to-MIDI remains available on platforms already supporting it. Extend both Writer and Song playback events/sinks to schedule duration-aware synthesized voices with a start and release time; the fixed 700 ms one-shot path is not used for sequenced melody notes. Harmony/save chord stabs keep their existing one-shot behavior. Convert note duration ticks to wall time with the shared tick rule. Stop/cancel releases all currently active sequenced voices.
- A guitar strum pattern stores 16th-grid events (tick plus down/up direction) and a loop length. Resolve its harmony source from `lane.anchorLaneId` when that id names a harmony lane in the section; otherwise use `primaryHarmonyLane(section)`, matching the existing save-lane fallback. If the resolved lane has no active chord at a strum tick, remain silent; do not fall through to another harmony lane. Each event plays that chord low-to-high on a downstroke and high-to-low on an upstroke. Strum tones have a 12 ms spacing and a gate of half the configured beat, clipped to the pattern/block end. This is a rhythmic chord strum, not tablature or exact fretboard fingering.
- `songFromSongwriter` maps each melody lane to a Song note track and each guitar-strum lane to a Song note track. Melody notes preserve pitch, timing, and duration. Extend `NotePatternNote` with backward-compatible optional millisecond onset and duration offsets; when a note is clipped by a pattern/block/section edge, shorten its duration by the delayed onset so the audible release stays inside the same window. Song live playback schedules each offset and note release, while offline rendering applies the same onset and duration in sample time. Thus each strum keeps its 12 ms string stagger on both surfaces without its late chord tones crossing the edge. Existing Writer audio lanes remain out of this conversion and must be identified as such in import summary/help.

Timing parity tests cover 4/4 and 6/8 at the same quarter-note BPM across Writer live playback, Song live playback, WAV sample positions, and audio clip onset, seek offset, and stop time.

### Phase 3 — Complete Record-to-Demo Loop

- Add a review/re-record step before committing newly recorded audio to a Song track. This phase's record/export target is the Song workspace. Writer audio lanes continue to play in Writer but are not imported by `songFromSongwriter` in this release.
- Extend WAV mixdown to include Song audio clips as well as note/drum tracks. Output is mono PCM16 WAV at 44.1 kHz; honor clip trims, track gain, mute/solo state, and Song timeline start ticks. Audio stays at source speed, matching current Song playback. Accept valid PCM16 little-endian WAV with 1 or 2 channels and sample rates from 8,000 through 96,000 Hz. Downmix stereo by averaging each frame and linearly resample to 44,100 Hz. Reject malformed headers, unsupported channel counts, rates outside that range, non-PCM16 WAV, and compressed audio during preflight.
- The repository can extract PCM16 sample data but currently does not validate all format tags/channels/rates for mixdown or decode MP3/M4A. Add strict WAV-header parsing and validate every referenced clip before rendering. If an asset is missing, compressed, or not an accepted PCM16 WAV, block export and list the clip with an actionable convert/re-import message; never silently omit audio. Honor the current audible-track rule (solo tracks only when any track is soloed, otherwise all unmuted tracks) across note, drum, and audio tracks. Apply trim start/end against native-rate samples before downmix/resampling.
- Route every tick-based audio helper (`songwriterAudioTickToMs`, `audioTickToMs`, and `audioClipLengthTicks`) through the shared quarter-note BPM conversion from Phase 2. Update `stretchTargetMs` to derive bar duration from `config.measureTicks * millisecondsPerTick`, not numerator × quarter-note duration. Audio clip start, seek offset, derived timeline length, stretch target, and stop time must agree with note events in the same tick grid, including 6/8.
- Generated-file platform matrix:

  | Platform | WAV mixdown | Song bundle export / import | Recovery JSON export |
  | --- | --- | --- | --- |
  | Android/iOS | Temporary file plus native share sheet; note/drum tracks and supported referenced PCM16 WAV clips | Native share sheet for export in Phase 3; native file picker for import in Phase 4 | Native share sheet |
  | macOS/Windows/Linux | Save dialog, then write bytes to the selected path; note/drum tracks and supported referenced PCM16 WAV clips | Save dialog plus direct byte write for export in Phase 3; native file picker for import in Phase 4 | Save dialog plus direct byte write |
  | Web | Browser share UI when the Web Share API is available, otherwise a download fallback, for note/drum-only Songs. If the Song references any audio clip, preflight blocks WAV export with a message to export from a native platform; Web has no supported audio-asset storage path in this release. | Bundle export is explicitly unsupported in Phase 3; bundle import is explicitly unsupported in Phase 4 because the audio repository is filesystem-backed and does not persist across reloads | Web Share API when available, otherwise download fallback |

  Every platform rejects malformed, missing, compressed, or unsupported audio clips before creating a partial WAV. Web note/drum-only export remains supported; it never silently omits a referenced audio clip. For native platforms, apply audio-track mute/solo rules to mixdown as specified above.
- Use one generated-file delivery path for WAV mixdown, Song bundles, and recovery JSON. Android/iOS write to a temporary file and open the native share sheet with the correct extension/MIME type, supplying `sharePositionOrigin` on iPadOS; macOS/Windows/Linux open `file_picker` without bytes and then write the full byte buffer directly to the returned path; Web uses the Web Share API when available and `share_plus`'s download fallback otherwise. Report success or cancellation according to the share result. Keep import bundle support native-only as already specified.
- Add a user-visible **Export Song Bundle** action in the Song overflow menu on Android, iOS, macOS, Windows, and Linux. Reuse the generated-file delivery path and `share_plus` introduced in Phase 1 for `.mzbundle`; do not repeat the Android Gradle Plugin change in this phase. On Web, show a clear unsupported-platform explanation for bundle export because the audio repository is filesystem-backed and does not persist across reloads. Add the direct [`archive: ^4.3.0`](https://pub.dev/packages/archive/versions/4.3.0) dependency for ZIP encoding; Phase 4 reuses it for decoding.
- A versioned portable Song bundle is a ZIP containing `manifest.json` (`format: "muzician-song-bundle"`, `schemaVersion: 1`, entries with source asset ID, format, exact path, and byte length), `song.json` (complete `SongProject` state), and `audio/<sourceAssetId>.<format>` for each referenced WAV/MP3/M4A source. Cap the complete archive at 100 MiB and each audio entry at the existing 50 MiB import limit; enforce both compressed and declared/extracted totals before any repository write.

### Phase 4 — Editing Safety, Bundle Import, and Documentation Closeout

- Add bounded, in-memory undo/redo history for these edits only:

  - Song: add/remove/rename/reorder/mute/solo/volume tracks; add/move/split/duplicate/trim/transpose/make-unique/delete clips; edit note/drum patterns; add/edit/remove markers; edit tempo, meter, and scale.
- Store at most 50 project snapshots per active Writer/Song workspace in memory. Undo/redo is project-scoped; changing project or loading a saved snapshot clears that workspace's history. Confirmed `Import from Writer` is one undoable Song transaction. Confirmed `New Song` or `New Writer Project` clears history with the new state. A new edit after undo clears the redo branch. Full immutable snapshots preserve shared pattern links and audio references.
- One committed edit creates one history entry: text fields commit on submit/focus loss, continuous drag/slider gestures commit once on release, and dialogs/pickers commit once after confirmation. The 50-snapshot cap means 50 undo steps plus the current state. Redo is cleared by any new edit. Project switch, loading a named save, New project, and opening a named snapshot clear history. `Import from Writer` and confirmed Song bundle import each form one undoable Song transaction.

## Out of Scope for This Initiative

- Accounts, cloud collaboration, and real-time co-writing.
- A general-purpose DAW feature set such as plugin hosting or advanced automation.
- AI-generated lyrics or arrangements.
- Exact guitar tablature, velocity-sensitive performance, and additional strumming/picking libraries.
- Importing Writer audio lanes into Song. The import UI and guide must state this boundary.
- MP3/M4A offline WAV mixdown. These assets remain playable and included in portable bundles, but export preflight requires supported PCM16 WAV sources.
- A full notation engraver. MIDI and printable chart exports can be reconsidered after the complete audio/project handoff is dependable.

- Do not start application-code implementation until a fresh-context reviewer approves this plan.
- The reviewer must inspect the plan, `PRODUCT.md`, `DESIGN.md`, and relevant existing code/docs; return `APPROVED` or specific blocking revisions.
- For each revision request, update the plan and send it to a new fresh-context reviewer. Continue until the reviewer returns `APPROVED`.
- After approval, delegate each implementation phase to fresh `gpt-6-luna` subagents at the highest reasoning setting exposed by this environment. Keep scopes bounded and phases sequential when later work depends on earlier model or store changes.
- Integrate each phase, run its acceptance checks, update its feature docs and `AGENTS.md` as needed, and use simulator review for visible layout/recording workflows when available.
- The approved dependency sequence is `share_plus: ^12.0.2` and its Android Gradle Plugin upgrade in Phase 1, then `archive` in Phase 3. Their platform roles are approved by this plan. If implementation finds either incompatible with the repository toolchain, or requires another dependency/platform integration beyond those choices, pause that phase and report the concrete decision needed. Pause as well if implementation requires changing the product direction.
