## Goal and agreed behavior

- Each Writer section owns one persistent folder directly below the selected project. Folder identity follows the section ID, so equal section names remain distinct. Section repeats do not create more folders.
- Every source `SongBlock` in every lane (harmony, silent/lyrics, save/voicing, drum, melody, guitar strum, audio) has one canonical `SaveEntry` and one persisted folder membership for its section. Repeated timeline renderings of one source block share that membership.
- A save may be placed in several sections through references to one canonical entry. Editing shared musical content updates every placement. **Make Unique** copies the save and detaches only the chosen placement. Bar position, span, and section-specific lyrics remain local to the placement.
- A Fretboard/Piano save made without a Writer destination stays in the project root as a free idea. Linking it into Writer does not move or duplicate it. Writer-created saves first live in their section folder; when their final block is removed, they move to the project root so work is not silently lost. Origin is stored on the save, so reusing a root idea never silently moves it.
- An existing root idea is linked only by an explicit **Use in Writer** action on that save. A fresh instrument selection creates a new canonical save. Never infer source identity from `SaveSystemState.activeSession`, which can be stale after edits.
- The Fretboard/Piano → Writer handoff prompts for an editable block/save name after the destination is chosen, before it commits. A custom name appears on the Writer block and in Saves. Writer's quick **Add chord** creates a named save too, with the chord symbol as default; the name remains editable in Writer and Saves.
- A linked voicing's Writer actions include **Edit in Fretboard/Piano**. This loads the canonical save into the instrument, switches workspace, and exposes **Update linked save**. The update writes the edited instrument snapshot to the same save ID, so all placements update. Switching project or loading a different save clears that edit target. Renaming a reused save changes the name in all placements; Make Unique gives one placement a separate name and content.
- Section folders are managed through Writer. Renaming, reordering, deleting, undoing, redoing, loading a named Writer snapshot, and switching projects reconcile the tree. The Save browser does not permit a manual rename/delete/move of a Writer-managed section folder. Deleting an in-use save is refused with an explanation; removing its last Writer placement makes it a root-level free save.
- A named **Song version** restores its saved block, voicing, pattern, clip, and lyric content. If a shared canonical save has changed since that version was captured, loading it forks a new Writer-owned canonical save from the version's retained fallback content (one copy per distinct original save ID, preserving sharing within that version). Original/root saves and other versions stay untouched; audio files remain shared by asset ID. Project tempo, meter, and key remain owned by the current project config: when they differ from the version's recorded values, show the user those differences before loading and apply the current project config to the materialized live session. The stored version is never retrofitted or rewritten. The loaded version is initially shown as clean, with its materialized content as the dirty baseline.

## Pre-implementation code and risks

- `lib/models/songwriter.dart` has `SongSection.id`, `SongBlock.id`, and an optional `saveId`; harmony and most other lanes currently have no save. `SongBlock.embedded` is a detached voicing fallback. There is no block-name field.
- `lib/store/songwriter_store.dart` creates/edits all blocks and holds the project-scoped, 50-step Writer history. `_set` is the central mutation path. `insertInstrumentSelectionAtBar` currently inserts a harmony block or embedded snapshot without a library save. `acceptVoicingSuggestion` and `acceptThirdAboveSuggestion` currently put saves at project root.
- `lib/features/instrument_shared/writer_handoff.dart` owns the destination picker and occupied-bar replacement confirmation. `lib/features/songwriter/songwriter_screen_sheet.dart` owns quick Add chord and block actions.
- `lib/models/save_system.dart` / `lib/store/save_system_store.dart` persist flat folder and save arrays under `@muzician/save-system/v3`; `SaveEntry` has one `folderId`. `lib/ui/save_browser_panel.dart` lists only physical folder children. `lib/features/fretboard/fretboard_save_panel.dart` and `lib/features/piano/piano_save_panel.dart` already allow saving at the selected project root.
- Writer working drafts (`lib/store/songwriter_sessions_store.dart`) and named Writer snapshots (`lib/features/songwriter/songwriter_save_panel.dart`) are separate from Save System saves. Persistence is split across keys. Reconciliation must be idempotent after a process stops between writes.

## Data model and ownership

1. Add optional `writerSectionId` to `SaveFolder`; leave existing folders unchanged. Add a `WriterSaveLink` collection to `SaveSystemState`, serialized in the current v3 payload with `[]` as the legacy default. A link is identified by the source `SongBlock.id` and has `sectionId`, `folderId`, `saveId`, and `laneKind`. It holds no duplicate snapshot bytes. A canonical `SaveEntry` continues to hold one `InstrumentSnapshot` and one physical `folderId`. Add a persisted `origin` enum (`manual` default for legacy/user saves, `writer` for entries created from Writer). The Save browser merges physical entries and links, deduplicating by save ID within a folder. Add `folderId` to `SaveEntry.copyWith` for rehoming.
2. Add an `InstrumentSnapshot` subtype, `WriterBlockSnapshot`, for Writer-native content. It records the lane kind and a placement-free musical payload: harmony/chord fields; silent-block data; drum/melody/strum pattern contents; audio clip metadata and full `AudioAsset` metadata for its source **and** derived stretch asset. Audio bytes remain in `SongAudioRepository`, subject to the existing retained-snapshot references rule. A save-lane voicing uses the existing `FretboardSnapshot`/`PianoSnapshot` instead. `InstrumentSnapshot.fromJson`, `toJson`, card labels, and filtering handle this new subtype. Unknown or corrupt legacy references remain visibly broken rather than fabricating musical data.
3. `SongBlock.saveId` becomes the canonical content reference for every new block. Existing `embedded` and chord/pattern fields remain as a legacy/fallback cache so old Writer JSON and interrupted writes are recoverable. For a linked block with a valid same-project `SaveEntry`, `resolveBlockSnapshot` and other content readers use the canonical save **before** `embedded`; fallback fields are read only when that save is missing or corrupt. Add an optional `name` only if the UI cannot read `SaveEntry.name` reliably for legacy/offline blocks; otherwise keep the name exclusively in `SaveEntry`. Do not put a second editable name in Writer state.
4. Keep the additive v3 JSON format. Hydration treats absent `writerSectionId`/`writerLinks` as legacy. On first open of each project, reconcile existing Writer blocks: reuse a valid same-project `saveId` **unless** the block has a legacy `embedded` snapshot and lacks a new `WriterSaveLink` (the old `makeBlockUnique` convention). For that case, create a **new** canonical save from `embedded`, assign its new ID, and preserve the detached content/name. For an already linked block, `embedded` is only its fallback cache. Create a canonical save from other embedded or Writer-native blocks when needed, create section folders and links, and preserve a broken reference when its content cannot be recovered. Never adopt an unrelated project’s save. The Writer snapshot retains fallback content for **every** lane, including pattern/clip and asset metadata; named Writer snapshots can repair a deleted former root link and restore an older musical version. Tests cover v3 round trips and old payloads; no destructive storage-key migration.

Illustrative model shape (names may be adjusted to match existing conventions):

```dart
class WriterSaveLink {
  final String blockId;   // one source block; repeated renderings reuse it
  final String sectionId;
  final String folderId;
  final String saveId;    // canonical SaveEntry.id, possibly shared
  final SongLaneKind laneKind;
}

class SaveFolder {
  final String? writerSectionId; // null for ordinary folders
}

enum SaveOrigin { manual, writer } // legacy JSON defaults to manual
```

## Mutation and consistency rules

1. Reconcile section folders, canonical saves, and links in one prepared Save System update. The Writer store assigns block `saveId`s and prepares entries; `SaveSystemNotifier.buildWriterStructure(projectId, next)` validates and prepares the Save System payload, then `commitWriterStructure(projectId, prepared, persist: false)` publishes it while the shared Writer transaction owns persistence. Include undo/redo and named snapshot load. Keep both Writer and Save System immutable. On cold start and project selection, run the same idempotent reconciliation before showing Writer. `lib/store/app_bootstrap.dart` must run this after both persisted stores hydrate and before mounting workspaces.
2. Creation: preflight destination and overlap first; then create a canonical save and link, set `SongBlock.saveId`, and commit one Writer history step. Cancellation and a failed overlap leave no save. For occupied repeated placements, replace the source block content while retaining its ID, placement, lyrics, and repeat pattern, then write through to its save. Repeated placements still have only one link.
3. Shared edits: update the canonical `SaveEntry.snapshot` and apply its musical fields to all blocks in the current project that reference the same save ID, preserving each block's placement and local lyrics. An edit to a `DrumPattern`, `NotePattern`, `GuitarStrumPattern`, or `AudioClip` must additionally find **every** block using that `patternId`/`audioClipId`, even when those blocks have different save IDs; refresh all affected canonical saves and their Writer fallback content in the same transaction. **Update linked save** from Fretboard/Piano uses the Writer sync coordinator: in one journaled transaction it updates the canonical instrument snapshot and refreshes the `embedded` fallback of **every** Writer block that references that save. Any other linked-snapshot mutation path must route through the same coordinator or be rejected by the ordinary `updateSnapshot` method; it cannot leave linked fallback caches stale. Playback and previews resolve the newest canonical snapshot. Do not sync local lyric changes into shared content. The explicit root-save **Use in Writer** route passes `SaveEntry.id` through the handoff payload and validates it immediately before commit; the fresh-selection route passes only its captured snapshot and creates a new entry.
4. Make Unique: copy the canonical snapshot to a new `SaveEntry`, assign the selected block the new save ID, and, for Writer-native pattern/clip metadata, clone mutable pattern/clip IDs while retaining the same audio source asset. The other blocks continue to reference the original save. This is one Writer undo step. Replace the existing `makeBlockUnique` detached-`embedded` behavior for linked blocks; retain compatibility when reading old detached blocks.
5. Removal: deleting a block removes its `WriterSaveLink`. A `manual` save keeps its original physical folder, including the project root; it is never rehomed by Writer. A `writer` save lives in its earliest surviving linked section folder, and moves to the project root only when no links remain. Linking a formerly removed `writer` save again moves it back to its first linked section. Deleting a section removes its links and folder, applying this origin-aware rule to every canonical entry. Undo recreates links, restores folder naming/order, and rehomes existing save IDs without making duplicate entries. The **store**, not only the browser, refuses direct deletion of a linked entry or managed section folder, and refuses arbitrary save/folder creation or rename/move under a managed section folder. The browser explains how to remove linked work from Writer first. Project deletion keeps its current cascading behavior.
   For `deleteFolder` on any *ordinary* non-project folder, calculate its complete descendant folder set first; if any canonical save in that subtree is referenced by any `WriterSaveLink`, reject the deletion and explain which linked saves must be removed/repositioned. This guard lives in `SaveSystemNotifier`, so a caller bypassing the browser cannot cascade-delete an in-use save. Explicit `deleteProject` retains its project-wide cascade and clears that project's Writer links/sessions.
6. Audio clips can be referenced by several block placements. Change `_removeAudioBlock` to remove a clip only after its final live block reference is gone; remove source or stretched `AudioAsset` metadata only when no live clip or retained Writer/save snapshot references it. Reuse a shared clip/asset for linked placements; Make Unique clones mutable `AudioClip` metadata and derived stretch state while retaining the source file. Apply the same reference check to slice/scatter removal and undo. Never serialize source audio bytes into SharedPreferences. Section export itself is a future feature, not part of this change.
7. Crash consistency: route **every** Save System mutation persistence (including instrument updates, rename, delete, and project selection), Writer draft persistence, and Writer named-save binding persistence through one serial queue. A Writer transaction captures immutable next Save System, Writer draft, and `WriterSaveBinding` payloads; its queue item writes a pending journal (project ID plus all three payloads), awaits Save System write, awaits Writer draft write, awaits binding write, then removes the journal. No other save, Writer, or binding write may run between these steps. A regular mutation queued later writes only after journal removal. Replace the Writer draft and binding stores' independent debounce writes on this path, so they cannot overtake the journal. A crash before the journal write completes can lose the latest in-memory gesture as with the existing draft; after it completes, startup rolls the transaction forward idempotently before exposing workspaces. Because later instrument edits cannot persist while a journal exists, replay cannot overwrite a newer durable save. Replay restores the binding and `alwaysOverwrite` flag together with a named-version load before the Save action is enabled, preventing a stale binding from silently overwriting another named version. For pre-journal legacy mismatches, preserve both differing payloads (move an orphan canonical save to the root and retain Writer fallback content) and surface a recoverable conflict rather than silently overwriting either. Add staged-failure tests for every queue/journal write boundary and recovery on next launch.
8. Named version save/load: when saving a named Song version, materialize every block's **current canonical** musical content and required pattern/clip/asset metadata into that `SongwriterProjectSnapshot` before writing the named entry; never trust a stale cache. When loading, compare each saved block's materialized fallback with its referenced canonical entry. Reuse an unchanged entry; for a changed or missing entry, create a new Writer-owned entry from the saved payload and remap every block that shared the old ID to the same new ID. Reconcile folders/links from that materialized snapshot in one Writer transaction. Do not overwrite a root manual save or mutate the old named `SongwriterProjectSnapshot`. `applyProjectConfig(retrofit: true)` must skip immutable named `SongwriterProjectSnapshot` entries; the active Writer session still follows the project master config. Before loading a version with different tempo, meter, or key, show a brief difference summary and explain that the current project settings will apply. Extend `WriterSaveBinding` with a persisted materialized-content baseline (or equivalent canonical-aware fingerprint) so `writerDirtyProvider` is false immediately after a successful load and becomes true after later block or linked-save content edits. Keep old binding JSON compatible; older bindings use their existing comparison until next save/load.

Implemented store boundary:

```dart
final prepared = _prepareWriterStructure(projectId, previous, proposed);
final sync = ref.read(writerSaveSyncProvider.notifier);
return sync.commitWriterTransaction(
  projectId: projectId,
  saveSystemState: prepared.saveSystem,
  writerDrafts: nextDrafts,
  writerBindings: nextBindings,
  commitMemory: () {
    saveNotifier.commitWriterStructure(
      projectId,
      prepared.saveSystem,
      persist: false,
    );
    sessions.commitState(nextDrafts);
    bindings.commitState(nextBindings);
    _applyState(prepared.project, persistDraft: false);
  },
);
```

## UI and file-level implementation steps

1. **Persistence/domain** (`lib/models/save_system.dart`, `lib/schema/rules/save_system_rules.dart`, `lib/store/save_system_store.dart`, `lib/models/songwriter.dart`, `lib/schema/rules/songwriter_rules.dart`): additive JSON fields and snapshot subtype; link resolution, folder reconciliation, shared-copy/Made Unique helpers, same-project validation, recoverable legacy paths. Implement the pending journal and serialized writes for Save System, Writer drafts, and named-save bindings in a small `lib/store/writer_save_sync_store.dart` coordinator rather than introducing circular notifier listeners.
2. **Writer state** (`lib/store/songwriter_store.dart`, `lib/store/songwriter_sessions_store.dart`, `lib/store/app_bootstrap.dart`, `lib/store/writer_save_binding_store.dart`): central sync and history handling for all lane kinds; snapshots for patterns and clips; audio reference ownership; update the two suggestion actions to place saves in the correct section folder; explicit Make Unique and rename-save operations. Materialize named Song versions without mutating their shared source saves and keep Writer's dirty indicator accurate.
3. **Handoff and Writer UI** (`lib/features/instrument_shared/writer_handoff.dart`, `lib/features/songwriter/songwriter_screen_sheet.dart`, `lib/features/songwriter/songwriter_screen.dart`, `lib/features/songwriter/songwriter_block_preview.dart`, `lib/main.dart`, plus a small shared name dialog in `lib/ui/` only if both callers need it): name prompt, quick Add chord save, visible block label and chord symbol, Rename and Make Unique actions, Open/Edit in instrument, graceful missing-save feedback. Preserve destination-change cancellation and occupied-bar confirmation.
4. **Save browser** (`lib/ui/save_browser_panel.dart`, `lib/ui/save_card_label.dart`, `lib/features/songwriter/songwriter_save_panel.dart`, `lib/features/fretboard/fretboard_save_panel.dart`, `lib/features/piano/piano_save_panel.dart`): display linked saves in managed section folders; distinguish a root free idea from a section link; route linked rename to canonical save; guard destructive operations; retain the root Save Here flow for standalone ideas. The Writer panel has separate **Song versions** (whole `SongwriterProjectSnapshot` save/load) and **Section blocks** (mixed linked `WriterBlockSnapshot`/instrument saves, browse/rename/**Use in Writer**) views. `Use in Writer` on a root Writer-native save opens the section/lane/bar picker, restores its pattern/clip/asset metadata from the save, preflights overlap, creates a new source block ID, and links the existing save; if that save is already used, both placements share edits until Make Unique. Its saved default lyrics are copied into the new placement once and thereafter remain local. Fretboard/Piano save panels expose **Use in Writer** for a selected save and **Update linked save** for the current explicit edit target. A Writer-native save must never be offered as a whole Writer project load.
5. **Documentation** (`docs/songwriter.md`, `docs/save_system.md`, `docs/fretboard.md`, `docs/piano.md`, `docs/song_writer_guide.md`, `README.md`, `PRODUCT.md` only if the product principle needs refinement): document the folder tree, shared edits, Make Unique, root free ideas, and recoverable removal. Review `DESIGN.md` and `AGENTS.md` after each phase; edit them only if a lasting visual token or repository rule changes.
